# Docker readiness healthcheck (CANDYS-30)

The `candystore` Compose healthcheck runs the Python stdlib HTTP client already in the image against `http://127.0.0.1:3001/readyz`. A 204 response exits zero; HTTP 503, refused connections and response timeouts exit nonzero. `/healthz` remains a separate DB-independent 204 liveness endpoint. `/readyz` checks DB connectivity only: it does not assert schema, insert capability, or write privileges.

The client timeout is 3 seconds, and Docker limits each check to 3 seconds. Checks run every 30 seconds with 10 consecutive failures required and a 5-second startup grace. Once an already-healthy container loses DB access, the nominal upper bound to Docker `unhealthy` is **10 × (30 + 3) = 330 seconds (5 minutes 30 seconds)**, allowing for Docker's scheduling/inspection overhead. The startup grace exempts failed checks *only while starting*; it does not extend the outage window after a healthy state. A recovered 204 check restores `healthy` on its next run (nominally within 33 seconds plus scheduling overhead). This is an operational check interval, not a guarantee that every ingest/query operation succeeds.

Source-only verification (no production Compose `up` or `down`):

- `docker compose -f compose.yml config --format json` renders configuration without starting services. `tests/test_readiness_healthcheck.py` separately asserts the literal configured `127.0.0.1:3001/readyz` target and health timing, then executes **adapted** copies of the rendered command against dynamically allocated 204, 503, delayed and refused host fixtures (only the port changes; the refused fixture holds a bound non-listening socket). If Docker Compose is unavailable, only these rendering/probe-dependent tests skip; the actual HTTP handler's `/healthz` and `/readyz` branches still run with patched DB connectivity. An isolated `docker run --network none` Python fixture also executed the **exact rendered command without substitution** against 204, 503, delayed and refused cases on port 3001; evidence is in the active profile scratch `candys30-exact-probe-repair.log` (not a production container).
- `mise run test` and `mise run lint` are repository entry points. DB-dependent suite cases require a guarded disposable `CANDYSTORE_TEST_DATABASE_URL`; skipped cases must not be counted as passed DB coverage.
- A disposable DB-outage proof used a separately named internal Docker network, test PostgreSQL and candidate app containers, with no host ports, production volumes, Dapr or Bloodbank attachment. Its recorded health logs show `unhealthy` after 299.92 seconds (10 failed checks) following only test-DB disconnect and `healthy` 36.4 seconds after reconnection; see active-profile scratch `candys30-docker-proof.log`. App, DB and network were removed. The proof used `docker rm -f` without `-v` and did not capture DB anonymous-volume mount IDs, so anonymous-volume removal cannot be established; no unidentified volumes were removed. This does not claim that the installed production app was restarted or is healthy.
