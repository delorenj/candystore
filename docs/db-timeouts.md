# CANDYS-31: database budgets and startup

Every app database operation (ingest, readiness, queries, context analytics, migrations) opens via `candystore.db.cursor` → `_connect`. `CANDYSTORE_CONNECT_TIMEOUT_SECONDS` defaults to **3 seconds** (positive integer). `CANDYSTORE_STATEMENT_TIMEOUT_MS` defaults to **5000 milliseconds** (positive integer). The latter is sent to PostgreSQL as a session-start `-c statement_timeout=...ms`, so the server cancels slow individual statements even if the client waits. It does **not** impose a deadline on an entire multi-statement transaction, network reads after connection, or an entire HTTP request.

Values must be positive decimal integers at most 2,147,483,647; zero, negative, fractional and invalid values fail before connecting. `DATABASE_URL` remains the connection identity and its unrelated libpq options survive. Effective connect timeout is the minimum of app setting, explicit DSN `connect_timeout`, and `PGCONNECT_TIMEOUT` (when present). Effective statement timeout is the minimum of app setting and the final preexisting `statement_timeout` in the DSN `options`, or `PGOPTIONS` when the DSN has no `options`. Invalid or unbounded explicit timeout settings fail closed. The final appended `-c statement_timeout=...ms` takes precedence while preserving other startup options. libpq normally gives DSN options priority over PGOPTIONS; that behavior remains. `context.latest_context` sets a transaction-local 2500ms timeout: it remains tighter than the 5000ms default. The shared bounded cursor retains an already tighter session timeout rather than letting that `SET LOCAL` relax it.

`main.run` calls `init_schema_with_deadline` before constructing the HTTP server. It forks a dedicated boot worker on POSIX; unsupported platforms fail clearly before starting a server. Four migration attempts at most, with sleeps of 0.25, 0.5 and 1.0 seconds (total 1.75 seconds). Retry only connection-class SQLSTATE 08*, 57P01/57P02/57P03, 53300, or recognizable connection failures without SQLSTATE (including a missing local PostgreSQL Unix socket). Statement cancellation, bad SQL, config failures and other errors fail promptly. The fourth transient connection failure propagates; the process exits unsuccessfully without an HTTP listener. Each failed SQL attempt rolls back and closes the connection via `cursor`.

`CANDYSTORE_BOOT_DEADLINE_SECONDS` defaults to **60 seconds** (positive integer). This is an **overall boot deadline**, from worker start through all connections, DNS resolution, migration statements, retries, sleeps and commits. If it expires, the parent terminates and reaps the worker (escalating to kill if needed), closing its DB socket; PostgreSQL aborts any uncommitted migration transaction. The boot worker also caps each server-side statement at no more than the configured deadline in milliseconds (without loosening a tighter setting), so a server query cannot keep running indefinitely after client termination. Startup never serves HTTP after timeout. This is not a per-request timeout or a guarantee that committed earlier migrations are undone; migrations are applied in one transaction per attempt. OS process cleanup may add up to roughly two seconds after the deadline, plus scheduling overhead.

Per-connection `connect_timeout=3` is applied by libpq **per resolved address/host**, not once across a multi-host DNS/DSN list; DNS itself and network reads outside connection establishment have no finite libpq bound. Per-statement 5000ms applies separately to each migration SQL execution, and a migration file can contain multiple statements. Thus **4 × 3s + 1.75s is not a worst-case boot time**. Without the overall deadline, the connection/statement/sleep budget would be up to four attempts times the sum of each resolved-address connect allowance plus each separately executed migration statement allowance, plus 1.75s sleeps and unbounded DNS/network/transaction overhead. The enforced overall deadline caps that aggregate wait at 60s by default (plus process cleanup/scheduling), regardless of host count or SQL statement multiplicity.

## Verification scope

The disposable PostgreSQL integration tests exercise real server-side statement cancellation, subsequent queries, analytics transaction caps, and boot deadline cancellation with no active slow backend after termination. The unit suite exercises transient and nontransient retry classification, timeout configuration, child reaping, and no HTTP listener before schema success. These checks do not migrate or deploy the live service.
